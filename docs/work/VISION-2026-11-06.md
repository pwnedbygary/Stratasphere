# Screenshots on the CPU (and the "it is loading forever" report)

Measured on 2026-11-06, RX 9070 XT 16 GB (gfx1201, Mesa 25.x Vulkan, ROCm 7.2.4), Ryzen 7 7800X3D,
31.6 GiB RAM, CachyOS. Model: Cyber-Tiel-Coder-35B-A3B, `UD-Q4_K_XL` GGUF, MTP head, BF16 mmproj
(`shared-vision/BF16/mmproj-BF16.gguf`, 902 MB). Router: `strata-native`, engine `llama.cpp` from the
Vulkan release build `0.4.0-dev / build 10909 / a2878d30d`.

## What the user saw

A fresh DeepSeek Harness chat against the local router answered the first turn in **1 m 48 s**, and the
next turn — a screenshot with a one-line question — never answered. The monitor showed "Prefilling,
216 new tokens read" and a prefill rate of 2.5 tok/s for minutes, then the router replaced the model
with "Backend stopped to preserve system memory headroom".

## What was actually happening

Three separate things, none of them a broken model:

1. **The first turn really did prefill ~100 K tokens.** The harness sends 331 tool schemas on every
   request: 363,872 bytes of JSON, **90,968 tokens by ÷4**, of which the REA MCP server alone is
   229 tools / 281,450 bytes (**70,362 tokens, 77 %**). One request measured 99,674 input tokens. At the
   observed 920–1,210 tok/s that is 82–108 s of prefill before the first token. Nothing was "filling
   context with nothing" — it was filling context with tool definitions.
2. **The screenshot turn ran the vision tower on the CPU.** `frontend/backend.hpp` always passed
   `--no-mmproj-offload`. Upstream llama.cpp offloads the mmproj by default; this fork forced the
   opposite for every profile.
3. **The memory guard then killed the backend, correctly.** With a 262,144-token context and the
   Q8_0 KV cache, the worker sat at 14.53 GiB of VRAM and 1.39 GiB free; a vision request on the CPU
   needs ~900 MB of host RAM for the projector plus graph buffers. The guard fired at
   `free RAM 4037 MiB (floor 4096), free VRAM 3316 MiB (floor 768), free GTT 2303 MiB (floor 768)`.

## The fix

- `frontend/backend.hpp`: `--no-mmproj-offload` is now passed only when the profile does **not** set
  `vision.gpu: true`. A profile without the key behaves exactly as before, so the default path is
  unchanged.
- `cyber-tiel-coder` profile: `vision.gpu: true`, context 262,144 → 131,072, `mtp: 2`, `ubatch: 512`.
  The context also lives in `~/.config/strata/native-tuning-router.json` (`"context"`), which overrides
  the profile's `--max-context`; both were set to 131,072.
- Router AppImage rebuilt from the patched tree (`tools/build_native_appimage.py`); 29.7 MiB.

Why 131 K: at 262,144 the model used 14.53 GiB VRAM (1.39 GiB free) and left no room for a GPU
projector. At 131,072 with the projector on the GPU it uses 13.44 GiB (≈2.5 GiB free), which is above
the guard's 768 MiB VRAM floor with room for an image encode.

## Measured before and after

Same machine, same model file, same 2,681 × 1,564 JPEG screenshot (the exact image from the failing
turn), context 131,072 in both columns:

| | vision on CPU (previous build) | vision on GPU (this build) |
|---|---|---|
| same screenshot, wall clock | **> 372 s, then the guard killed the worker** (`free RAM 4037 MiB < floor 4096`) | **6.8 s** |
| 1,200 × 400 text image, wall clock | not re-measured (the small image did answer in 1.6 s with CPU vision) | **3.3 s**, reads the exact strings back |
| threads during the encode | 8 pinned at 100 % CPU, GPU 6–12 % busy | GPU busy, CPU idle |

Honest caveat: the CPU column is not "slow but fine". It exceeded 6 minutes and then died on the RAM
floor, which is exactly the user-visible failure. PR #28320 upstream measured 22.4 s of CPU encode for
1,048 image tokens against 3.6 s on the GPU; this image is 4,188 prompt tokens, so tens of seconds was
the optimistic expectation and this machine took far longer.

Other numbers from the new build (context 131,072, `ubatch 512`, 26 CPU expert layers, MTP 2):

- model load: **16.1 s** (llama's own log, `model loaded` at 0.16 s of its run)
- cold 98,871-token text prompt: **81.5 s** → 1,213 tok/s prefill
- the same prompt again (cache hit): **0.6 s**
- decode, 220 tokens of prose: **46.0 tok/s**; MTP drafted 410 tokens and had 247 accepted (60.2 %)
- VRAM with model + projector loaded: 13.44 GiB of 15.92 GiB

## What to do in the harness (biggest single win)

The 88.2 K tool block is the cost, not the model. Disabling the REA MCP server for local-model
sessions removes ~70 K tokens: in `~/.dsh/profiles/web/cordis.patch.yml` add `- id: mcp-rea` with
`disabled: true` (or launch with `dsh web --patch ./local.yml`). The tool block then measures ~20.6 K,
which at the rates above is roughly a 25 s first turn instead of 82–108 s. `--profile` gives the same
isolation per installation.

## Upstream context

- llama.cpp offloads the mmproj by default (`mtmd_context_params.use_gpu = true`); `--no-mmproj-offload`
  is the opt-out, and it also turns off the whole CLIP graph's GPU path.
- [#17801](https://github.com/ggml-org/llama.cpp/issues/17801) reports the CPU projector being
  "terribly slow"; [PR #28320](https://github.com/ggml-org/llama.cpp/pull/28320) quantifies it.
- [#29629](https://github.com/ggml-org/llama.cpp/issues/29629) reports wrong image embeddings when the
  CLIP graph runs with flash attention on Qwen3.5/Qwen3-VL-family projectors, and
  [#28840](https://github.com/ggml-org/llama.cpp/issues/28840) a Vulkan device-lost with CLIP FA. There
  is no projector-specific FA flag in this build; the only switch is the global `--flash-attn`, which
  would also slow the text model. The correctness check above (reading `HELLO-VISION-7382` and
  `line two: 9184-ALPHA` back from an image) passed with the projector on the GPU, so this projector on
  this driver is not affected in practice. If images ever start misreading, set `vision.gpu: false` in
  the profile, which restores the previous CPU path exactly.

## Rollback

- AppImage: `~/Applications/strata_model_router.appimage.bak-20261106-cpuvision` (the build that forced
  CPU vision). `.bak-20261106-prev` and `.bak-20261105-cybermtp` are older still.
- Profile: set `"mtp": 0` to disable MTP drafts, `"vision": {"gpu": false}` to put the projector back on
  the CPU, and `"context": 262144` in `native-tuning-router.json` to restore the long context.

## Not measured here

- Why the CPU projector took > 372 s instead of the ~90 s that the upstream per-token numbers suggest;
  the likely cause is host-RAM pressure (the guard saw 4,037 MiB free) rather than a deadlock — the 8
  threads were inside llama's own clip graph, and `perf` attributed 99 % of samples to the llama binary,
  not to the driver or the kernel.
- Whether the shipped `a2878d30d` binary still contains the unterminated `server_tokens::push_back`
  loop that [#29865](https://github.com/ggml-org/llama.cpp/issues/29865) describes; the pinned source
  `3cf03257` does contain it, but no prompt path in that tree reaches it.
